High level · Tool independent

Grafana Cloud vending service

The platform owns a repeatable service definition. A request selects a market and its required capabilities; the delivery engine configures the stack and exposes an operating contract.

Terraform, Crossplane and direct API automation can implement the concept. Selection, dependencies, drift ownership, rotation and retirement must be designed explicitly; the delivery tool does not make them automatic.

Sources: Cloud stacks; reference ownership model.

Mid level · Resource anatomy

A market stack, opened up

The foundation, stack-local resources and external dependencies occupy different scopes. This cutaway names the resources that a market can select instead of treating the stack as an empty destination.

This is an available-capability map, not a default object count or a physical deployment map. The managed-kind atlas disambiguates repeated names and lists all activated GVKs. Cloud acceptance is not established by rendering.

Identity settings differ beyond the provider name

  • UK / Entra ID: dedicated application registration, tenant-specific authorization/token endpoints, UK group claim mapping, strict role mapping and a separate secret reference.
  • Germany / SAML: market IdP metadata, entity/ACS configuration, assertion attribute mappings, signed assertion policy and group-to-team bindings.
  • France / Okta: market application, issuer/endpoints, scopes, allowed groups, role mapping and credential references.
  • Poland / generic OAuth: market endpoints and client registration, group and role claim paths, scopes and login admission rules.

Changing IdP type is a migration requiring login and rollback validation. Profile labels alone do not create IdP registrations.

A common telecom dashboard pack

  • Every market: NOC overview, ingest health, platform usage and service availability.
  • RAN: site availability, radio-access latency, handovers and saturation.
  • Core: registration/session success, signaling and packet-core performance.
  • Fixed: access-network and broadband service health.
  • Digital: customer application latency, errors, frontend signals and journeys.
  • Security: SOC data views with explicitly reviewed access.

These telecom packs are proposed content, not dashboards shipped by this reference. Queries need market-owned metrics, labels and data sources.

Mid level · Identity joins and query enforcement

Market identity and access

SSO maps identity and claims. Teams participate in role assignments, content ACLs and data-source policies in parallel. A user query then follows the permitted data path.

The renderer requires supplied Team UID/ID values for datasource access and basicAuth; it does not discover them. Current docs say no applicable team rules can leave logs/metrics unrestricted. Multi-team/rule behavior, backend support and trace-preview constraints need explicit design. SCIM is refused by this reference.

Sources: authentication; RBAC; LBAC; team/role renderer; data-access renderer.

Mid level · Ownership, API surface and reconciliation

Crossplane control plane

This implementation has separate delivery, composition, provider and secret controllers. The function emits a complete desired set; it does not call Grafana APIs itself.

Argo must not manage the generated child objects. The credential bridge and readiness dependencies are expanded separately. Inventory GVKs remain observe-only; enabling a kind does not authorize every request to create it.

Sources: architecture; function registry / orchestration; provider and activation policy; ApplicationSet.

Mid level · Dependency graph with separate credential lanes

Stack bootstrap and credential handoff

The administrator, telemetry publisher and Fleet chains have distinct identities and consumers. ESO owns secret materialization and publication; the provider owns generated token resources.

Organization credentials are prerequisites, not request-supplied values. Admin publication reverses direction in row three to show the handoff. Provider-assigned IDs are observed, not derived. Retain does not guarantee survival of MR-owned connection Secrets.

Sources: core renderer and bridge; telemetry policy; Fleet credentials; secret lifetime and rotation.

Mid level · Routing, escalation and schedule dependencies

Alerting and incident response

The market service needs declared rules, one routing authority, delivery receivers and an independently owned responder schedule. Those resources have different lifecycles and ownership.

The diagram combines configuration dependencies with the alert-delivery direction; it is not a message trace. A same-stack observed integration is required for the routing join. Schedule ownership and external people, channels and transport prerequisites remain explicit.

Sources: alert bundles; routing tree; integration join; OnCall renderer.

High level · Optional fleet architectures

Shared operations across markets

Sixteen stacks do not automatically produce a group NOC dashboard. Choose how operators gain visibility and make the access, query and data-movement paths explicit.

These are design choices for an adopting telecom, not features automatically installed by this repo. Its GrafanaProjectContent API supplies a bounded central-data-to-project bridge, not generic sixteen-market federation. Option B needs a separate, reviewed data-source and credential design; option C needs a separate telemetry pipeline.

Sources: stack isolation; current bounded cross-stack contract.

Evidence and scope

Current reference implementation

Resource labels and ownership derive from source revision a914fd8. The atlas names the complete activated GVK map; the API table covers the complete current renderer registry. These counts describe types, not objects created per stack.

Rendering proves emitted configuration. Provider acceptance and live behavior are not exercised, and not exercisable here. Current official LBAC guidance has provisioning caveats alongside an IaC example; the diagrams do not resolve that ambiguity.
